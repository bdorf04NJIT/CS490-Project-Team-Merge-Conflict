  1. API client: frontend/src/api/targets.ts

  I added the code that fetches the summary from the backend, at the end of the
  file.

  STAR_VALUES = ['5', '4', '3', '2', '1']
  These are the star levels as strings, because the backend's
  rating_distribution uses string keys ({"1": n, ..., "5": n}). They're ordered
  highest first so the component can loop over them directly to show 5 stars at
  the top. The same constant is used to check the response, so both stay in
  sync.

  ReviewSummary type
  Describes the three fields the UI uses: review_count, average_rating (null
  when there are no reviews) and rating_distribution. The backend also returns
  target_id and latest_ingestion, which the workspace already gets elsewhere, so
  the type leaves them out.

  isReviewSummary(body)
  Checks the response before the UI trusts it:
  - review_count must be a number.
  - average_rating must be a number or null.
  - All five star keys must exist in rating_distribution and be numbers.

  If any of these fail, the request is treated as an error, not shown as blank
  or broken numbers. getTarget and listReviews already work this way.

  getReviewSummary(accessToken, targetId)
  Follows the same pattern as the other API functions in the file:
  1. Request: calls GET /api/targets/<id>/summary with the bearer token. The id
     goes through encodeURIComponent, so a value like a/../b can't change which
     URL is called.
  2. Network failure: if fetch itself fails (offline, server down), it throws
     "Unable to connect…".
  3. Error status: reuses the existing GET_MESSAGES:
     - 401 shows the session-expired message.
     - 404 shows the generic "doesn't exist or you don't have access" message. A
       missing target and someone else's target look the same, so nothing about
       other users' data is revealed.
     - Anything else shows "Unable to load the review summary right now."
     - The server's own error text is never shown to the user.
  4. Bad response: fails the shape check above, so it throws the same fallback
     message.

  2. New component: frontend/src/components/ReviewSummary.tsx

  Props: accessToken, targetId and refreshKey, the same as ReviewList. The
  workspace changes refreshKey after an ingestion or CSV import, which makes the
  summary reload.

  Loading:
  - A useEffect calls getReviewSummary.
  - Each request has a key (targetId:refreshKey:retry), and the result is stored
    along with that key. If the key changes, old data is ignored and the
    loading state shows again. This means stale numbers from another target or
    an earlier import are never shown.
  - A cancelled flag stops a slow earlier request from overwriting the result of
    a newer one.
  - The extra retry counter lets Try again start a new request.

  The four states it can show:

  ┌─────────────────────┬───────────────────────────────────────────────────┐
  │        State        │                What the user sees                 │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Loading             │ "Loading review summary..." (role="status", so    │
  │                     │ screen readers announce it)                       │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Error               │ Red alert panel with the message and a Try again  │
  │                     │ button (role="alert")                             │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ No reviews          │ "No reviews yet. Start ingestion or import a      │
  │ (review_count ===   │ CSV." (wording taken from docs/ui-ux-context.md)  │
  │ 0)                  │                                                   │
  ├─────────────────────┼───────────────────────────────────────────────────┤
  │ Has reviews         │ The summary card below                            │
  └─────────────────────┴───────────────────────────────────────────────────┘

  The heading "Review summary" shows in every state, so the section doesn't
  appear and disappear while loading.

  The summary card:
  - Reviews ingested: review_count from the backend. This is the true total of
    saved reviews. The review list's "100+" label stops at 100 because the list
    endpoint returns at most 100 reviews.
  - Average rating: shown as "3.4 out of 5".
    - It uses Intl.NumberFormat with 1–2 decimal places, so 4 shows as "4.0",
      3.4 as "3.4" and 3.75 as "3.75".
    - The backend already rounds to 2 decimals, so the frontend doesn't round
      any further.
    - If the average is ever null while the count is above zero (which shouldn't
      happen), it shows "—".
  - Rating distribution: one row for each star level from 5 down to 1. Each row
    has three parts:
    - A "5 ★" label.
    - An amber bar showing that star level's share of all reviews. This is
      calculated from the backend's counts, purely for display.
    - The exact count.

    Screen readers skip the bar and read a label like "5 stars: 2 reviews" or "1
    star: 1 review" instead. A small plural() helper picks "star"/"stars" and
    "review"/"reviews".

  Where the numbers come from: a comment in the code notes that nothing on this
  card is calculated from the review list. Every number comes from the backend
  summary, which is calculated from the reviews saved in the database. That
  covers the "calculated from persisted review data" requirement. It also covers
  the business rules the backend already handles:
  - Skipped records are never saved, so they aren't counted.
  - Failed runs save no reviews.
  - Fractional ratings like 4.5 count toward the lower whole star (the 4-star
    row), but the average still uses the exact value.
